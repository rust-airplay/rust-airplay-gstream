# 架构

English: [ARCHITECTURE.md](ARCHITECTURE.md)。

这个 crate 是 [`rust-airplay`](https://github.com/rust-airplay/rust-airplay) 所定义渲染器边界的一个实现。它解码编码帧并播放；它不解析 AirPlay、不打开套接字、不知道 `SETUP` 是什么。

## 两种媒体，两种形态

两条流以不同形式到达，后端也以不同方式播放：

| | 音频 | 视频 |
| --- | --- | --- |
| 帧边界 | 一次 push 就是一帧；编码帧没有起始码 | 字节流里的起始码 |
| 播放方式 | 链接 `libgstreamer`，每帧一个缓冲区经 `appsrc` | `gst-launch-1.0` 子进程，帧写进它的标准输入 |
| 原因 | raw AAC-ELD 帧既无同步字也无采样率，字节流说不出帧在哪里结束 | H.264 与 H.265 带起始码，解码器自己找得到边界；子进程让后端不必编译 C、也不必写 unsafe |

两个选择在 crate 的模块文档里也有说明。音频是链接 C 库的那条路径：`gstreamer` 与 `gstreamer-app` 在进程内使用，所以构建这个 crate 需要 GStreamer 开发文件，而运行只需要运行时插件。

```text
audio:  appsrc ! queue ! avdec_aac ! audioconvert ! audioresample ! volume ! <sink>
video:  fdsrc ! h264parse ! avdec_h264 ! videoconvert ! video/x-raw,format=I420 ! <sink>
```

确切的视频链取决于 sink，因为 sink 与解码器是一个选择：`d3d11h264dec` 解到只有 `d3d11videosink` 能接收的 Direct3D11 内存，而其他 sink 前面都要 `videoconvert`。`Options::with_video_sink` 同时替换 sink 与整条链，所以调用方应当用它，而不是分别设置这两个字段。

## 一帧数据会经历什么

- **视频**按推入顺序写进管线。时间戳不会进入管线：子进程被喂的是字节流，而字节流没有时间戳。因此节流发生在本侧。核心要求间隔时，`VideoStream::set_pace` 在帧之间睡眠；而核心通常不要求（`Config::pace_video` 默认关闭）。
- **音频**保留时间戳：每帧变成一个 `appsrc` 缓冲区，其呈现时间由客户端的采样计数换算而来，于是 sink 按采集时的速率播放。管线使用 `sync=false`，因为客户端的时钟与声卡的时钟不是同一个时钟；用一个去排程另一个，正是接收端卡顿的来源。
- **音量**是紧贴 sink 之前的 `volume` 元素。`Renderer::set_volume` 为之后打开的流保存增益，并设置正在播放的元素的属性。核心只说线性增益，从不说分贝。

## 预热

启动视频管线在它能接收帧之前要花约 700 毫秒：窗口与图形设备是在管线启动时出现的，不是在首帧到达时。`warm_video` 让管线随接收端启动，于是这笔开销在客户端连接之前付掉，而且下个会话复用这条热管线而不是重建。默认关闭，因为热管线意味着还没投屏屏幕上就有一个窗口——电视会这样，桌面应用可能不该。

## 冲刷与关闭

`flush` 在两条流上都是空操作，这是真实的限制，不是设计选择：

- `gst-launch-1.0` 管线是一个由管道喂数据的进程；字节流没有带内冲刷信号，所以已经写进去的帧仍会被解码并显示；
- `appsrc` 管线若不结束流，无法丢弃已经推入的缓冲区。

限制损害的是解码器本身：出现缺口后，视频解码器会在下一个关键帧重新同步，核心的队列也因同样原因在关键帧重启。实际影响是，一次冲刷最多让管线里已缓冲的帧在屏幕上多停留一小会儿。需要精确冲刷的后端必须自己在进程内拥有管线，这也是未来进程内视频路径会做的事。

`close` 用流结束事件结束音频流，让解码器排空；视频管线只在非热时关闭。`Drop` 会停止两者：让管线继续运行，会让一块声卡或一个窗口在进程存活期间一直被占着。

## 失败

`RenderError::Unavailable` 用在机器做不到被要求的事情时：`PATH` 上没有 `gst-launch-1.0`、sink 或解码器元素未安装、没有声卡。`RenderError::Failed` 用在管线接受了请求之后失败时。两种情况接收端都会报告并继续服务；在内部自动重试的后端是在隐藏自己的失败。

子进程的标准错误写到临时文件而不是管道：没人读的管道会填满并阻塞子进程，而这份输出恰恰是管线失败时想要的。`AIRPLAY_GST_KEEP_STDERR=1` 会保留该文件并在管线结束时打印路径，这是在无控制台环境下诊断失败的办法。

## 测试

单元测试构建管线描述，检查容易做错的决定：sink 会带着它的解码器一起换、HEVC 得到 HEVC 链、每条管线都明确写出 parser 与解码器。它们不需要 GStreamer。

集成测试从真实会话里抓帧——一个 H.264 关键帧及其后续帧、一个 AAC-ELD 负载、一秒长度的实测流——并把它们推过真实管线进入 `fakesink`。它们带 `#[ignore]`，因为需要 GStreamer 运行时；也正是它们能抓住"接受每个缓冲区却一个都没解码"的管线。运行方式：

```sh
cargo test -- --ignored
```
