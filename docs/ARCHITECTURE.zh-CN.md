# 架构

英文版：[ARCHITECTURE.md](ARCHITECTURE.md)。

本 crate 是 [`rust-airplay`](https://github.com/rust-airplay/rust-airplay) 定义的渲染边界的一种实现。
它解码编码帧并播放；它不解析 AirPlay、不开套接字，也不知道 `SETUP` 是什么。

## 两种媒体，两种形态

两种流以不同的形状到达，后端也用不同的方式播放它们：

| | 音频 | 视频 |
| --- | --- | --- |
| 帧边界 | 一次 push 就是一帧；编码帧没有起始码 | 字节流里有起始码 |
| 播放方式 | 进程内 linked `libgstreamer`，每帧一个 buffer 走 `appsrc` | `gst-launch-1.0` 子进程，帧写进它的标准输入 |
| 原因 | 裸 AAC-ELD 帧既没有同步字也没有采样率，字节流无法表示一帧在哪里结束 | H.264/H.265 带起始码，解码器能自己找边界；解码器在别的进程里，崩了也只带走自己 |

这两个选择在 crate 的模块文档里也写了。音频这条是链接 C 库的那条：`gstreamer` 与 `gstreamer-app`
在进程内使用，所以构建本 crate 需要 GStreamer 的开发文件，而使用它只需要运行时插件。

```text
音频：appsrc name=audio_source ! queue ! avdec_aac ! audioconvert ! audioresample ! volume ! <sink>
视频：fdsrc ! h264parse ! avdec_h264 ! <sink> sync=false
```

## 各模块负责什么

| 模块 | 回答什么问题 |
| --- | --- |
| `lib.rs` | crate 的公开面：`Options`、`GstRenderer`、sink 常量，以及集成测试用来搭管线的隐藏 `testing` 模块 |
| `options` | 调用方可以选什么，以及环境变量如何读进这些选择 |
| `options::sink` | sink 片段可以写什么 |
| `renderer` | `Renderer` 的实现：开流、音量、warm 管线 |
| `video` | 视频流：它的管线参数、节奏、flush |
| `audio::engine` | 一条音频流：`appsrc`、时间戳、flush、close、Drop |
| `audio::thread` | 一条管线运行其上的 GLib main loop |
| `audio::graph` | 构造音频管线所用的 caps 与描述串 |
| `audio::clock` | 由客户端的采样计数得出某一帧何时到期 |
| `pipeline` | 一个 `gst-launch-1.0` 子进程：启动、写入、收尾、重启 |
| `pipeline::writer` | 往它的标准输入写入的线程与队列 |
| `pipeline::stderr` | 它的输出去哪里 |
| `pipeline::error` | 它为什么起不来，以及渲染边界据此给出什么错误 |

拆分的依据是「问题」而不是「行数」：这里的每个文件就是回答一个问题的那段代码，
`#[cfg(test)]` 测试就摆在被测内容旁边。

## 视频管线

参数是作为列表构建的，不是拼成一个字符串、也不是把一个字符串切开：caps filter 里有逗号和空格，
而各平台对它们的引用规则不同，只有在 Windows 与 Unix 上都能通过 `Command` 的形式才是 token
列表。`gst-launch` 会再把参数合起来，所以管线本身是一样的。

sink 是一段片段——一个元素加上它的属性——校验发生在构造渲染器时，而不是第一帧到达时。片段不能含
链分隔符、不能带引号，第一个 token 必须是已安装的元素：把调用方的字符串直接拼进管线描述，是「一个配置
选项变成管线的第二条分支」的经典来源，而那条分支里的 `filesink` 就是把一次会话写进磁盘的办法。

往子进程写可能阻塞，只要子进程不读，就能阻塞任意久，所以写发生在自己的线程上，前面隔着一个只有几个
buffer 深的队列。一次 push 交出帧，然后有界地等写线程接走；一个不再读的管线于是表现为「这一帧被拒」，
而不是「这次会话永不返回」。每一次等进程也都有截止时间：正常关闭的管线有一段时间把剩下的播完，被杀的
进程有一段时间被回收，超过就杀掉而不是继续等。

## 一帧会经历什么

- **视频**按 push 的顺序写进管线。时间戳不会进管线：子进程吃的是字节流，字节流没有时间戳。因此节奏
  在这一侧：`VideoStream::set_pace` 在帧之间睡眠，而核只在 `Config::pace_video` 关闭时才调用它，
  否则是核自己在等。
- **音频**保留时间戳：每帧成为 `appsrc` 的一个 buffer，呈现时间是「距本次会话第一帧的采样偏移」，按
  会话采样率换算。偏移保存在客户端自己的 32 位里，用回绕减法求差，因为音频时间戳是会被回绕的 RTP 计数器：
  把它扩展宽度的接收端，在长会话之后就不再有经过时间。管线用 `sync=false`，因为客户端的时钟和声卡
  的时钟不是一个时钟，拿一个去调度另一个，正是让接收端卡顿的原因。
- **音量**是紧贴 sink 之前的一个 `volume` 元素。`Renderer::set_volume` 既为之后打开的流记住增益，
  也设置当前正在播的那个元素的属性。核说的是线性增益，从不说分贝。

## Flush

flush 的含义和 seek 一样：尚未播出的内容被丢弃，解码器忘掉它本来还想引用的帧。

- **音频**回到 `READY` 再回到 `PLAYING`。元素状态可以从任何线程改，所以这不需要管线自己的循环配合；
  而 `READY` 正是清空「源到 sink 之间所有队列」的那个状态。首帧锚点也一起丢掉，于是下一帧开始一条新的
  时间线。
- **视频**换掉解码进程。`gst-launch` 管线没有 flush 信号，也无法让解码器忘掉已排队的内容，所以持有它的
  进程被停掉，再用同样的参数起一个。这要付一次管线启动的代价，那就是「真正丢弃已排队媒体」的诚实价格。
  客户端在 flush 之后发来的关键帧，才让新解码器「正确」而不只是「空」。

## 预热

视频管线从启动到能接受一帧大约要 700 ms：窗口和图形设备是在管线启动时起来的，不是在第一帧到达时。
`warm_video` 让它在接收端启动时就起来，于是这份代价在客户端连上之前就付掉了；下一次会话复用一个
warm 管线，而不是把它拆掉。渲染器自己留着一个句柄、流也拿着一个，所以关闭会话不会拆掉管线；只有遇到
它放不了的编码，或者进程已经死了，才会重新起一个。它默认关闭，因为 warm 管线意味着「还没镜像任何东西，
屏幕上就已经有窗口了」——电视能接受，桌面应用未必。

## 关闭

`close` 用 end-of-stream 事件结束音频流，并等管线走到流的末尾，于是声卡自己的队列也算会话的一部分；
超过两三秒就不再等。`Drop` 在没调用过 `close` 时结束流、通知管线线程停止并等它：一条比自己的线程
活得久的流，会把声卡一直占到这个进程结束。视频一侧是同样的形状——`close` 收掉进程，除非管线是 warm
的；`Drop` 负责停。

## 失败

`RenderError::Unavailable` 用于「这台机器做不到所要求的事」：`PATH` 上没有 `gst-launch-1.0`、
sink 或解码器元素未安装、没有声卡。`RenderError::Failed` 用于「管线接受了请求，然后失败」。元素缺失
属于前一种，即使它是从 `gst-launch` 自己的输出里发现的——因为调用方得到的答案不同：一台放不了的机器
应该知道是环境不完整，而不是它的客户端坏了。两种情况接收端都会上报并继续服务；在内部重试的后端只是在
掩盖自己的失败。没有 `gst-launch-1.0` 的机器仍然能放音频：渲染器构造得出来，只有视频请求会说它不可用。

子进程的标准错误写进临时文件而不是管道：没人读的管道会填满并阻塞子进程，而这些输出恰恰是管线失败时最
想要的东西。文件是独占创建的，所以同时启动两个接收端不会共用一份日志；在平台有权限概念的地方以 0600
创建，因为解码器可能在错误里带出码流自己的参数；读回时最多 64 KiB。`AIRPLAY_GST_KEEP_STDERR` 会保留
该文件并打印路径，这是没有控制台时诊断失败的方式。

## 测试

单元测试构建管线描述，检查那些容易搞错的决定：HEVC 用的是 HEVC 的链、每条管线都点了 parser 与 decoder、
sink 片段夹带不进一条分支、时间戳在客户端计数器回绕处回绕。它们不需要 GStreamer 运行时。

集成测试把真实字节推过真实管线：一段 Annex-B 流进入 `filesink`、四十个裸 AAC-ELD 负载进入音频管线、
以及一次会话量的帧走渲染器构建的同一条路径。它们被 `#[ignore]` 标记，因为需要 GStreamer 运行时；
而它们才是能抓住「管线收下每个 buffer 却一个都没解出来」的那一类。视频 fixture 是合成的，
[tools/make-fixtures.sh](../tools/make-fixtures.sh) 能逐字节重新生成；音频那个是采集的，因为没有可用的
AAC-ELD 编码器来合成。[`tests/fixtures/README.md`](../tests/fixtures/README.md) 记录了每个文件是什么。

```sh
cargo test                  # 单元测试
cargo test -- --ignored     # 需要 GStreamer 运行时
```
